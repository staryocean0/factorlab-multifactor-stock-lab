## 3. 为什么尚不能签成完整条件信息归因

### A. F 的历史数值路径没有由三个 wrapper 文件完全绑定

本地复用记录核对了 fit-prefix、training、preflight 三个 blob；但真实建模和初始化还导入 `reaka_paper_v1.py`、`reaka_stage6_daily_engine.py` 和 `reaka_stage6_parameter_calibration.py`。报告没有提供本次实际加载这些实现的文件身份。小 batch 中“当前 F 适配器等于当前 base”只说明适配器恒等，不证明当前 base 等于历史 F 的全部数值路径。

此外 H 用 CPU，原 F 来自 CUDA。本地已主动披露，云端不会将其隐藏成设备一致。相同 seed 或 deterministic 设置不保证跨设备/版本完全一致（参见 PyTorch 官方 Reproducibility 文档的这一明确限制）。这不是已经测得硬件偏差，也不是重训的充分理由；它意味着在没有额外桥接证据时，当前差值是**混合运行环境的回顾性对照**，不能把每一部分差值唯一归给 X。

normalizer 被 `normalizer_from_store` 重新计算，wiring 记录了其摘要，但未把它与 F 原 normalizer 的身份明确对应。脚本检查 input manifest 字节，却未再次绑定训练/评价坐标及数组；原 R2/NOFIT 的适用身份记录可复用，不要求重做全闭包。需要的是本轮实际消费与已有证据的对应说明，而不是整仓源码白名单。

### B. 逐种子评价缺失，checkpoint 保存说法缺乏代码支持

设计第 5 节要求每 seed 与原 rank-z 集成都报告。当前 `seed_fit_receipts.json` 只有训练损失和分数文件摘要；`paired_daily.csv` 只有集成 F/H 和四个 B，没有每 seed 的评价。因此不能判断增量是否集中在某个 seed。这可直接从六份 H 与六份 F 已存分数导出，不需要任何模型推理或重训。

本地反馈称 H 权重留在本地，但提交的 runner 在评分后只保存 `h_review_scores_...npy`，然后 `del model`，未调用 checkpoint/state 保存。不能据此断言所有外部保存都不存在，却也不能签署“六份 H checkpoint 已绑定”。如果确有其他保存步骤，给路径与摘要；如果没有，明确记录未持久化。**不允许重训后把新权重冒充原 run02 权重，也不要求为补这句话重训。** 分数级统计仍可复算，checkpoint 级重放则保持不可验证。

### C. 小偏差和执行器局限不应变成大返工

原 NOFIT 将历史 epsilon 转 float64 后求均值；新 runner 的基准路径在 float32 上求均值。1430 的 2017-05-24 出现一处均值基准 rank tie 变化，均值反转总体 IC 从 0.13322081415939868 变成 0.1332208232482858，约 9.09e-9。它不改变 F−H，组差/Top30 也未变。使用原已验收 B 或明示 dtype 即可，不重拟合、不修改历史回执。

原 runner 有三个依赖个人绝对路径的 skip 测试；最后一个测试重复了 guard 条件，没有调用 runner.main。云端保留本地 4 passed 的执行声明，但实际云端运行是 1 passed / 3 skipped。新增云端检查直接调用原 main，验证现有输出和 data/output 内新路径均拒绝，3 passed。无需为让这些本地集成测试变绿而伪造 FactorLab 路径。

源码中的 `failed` 总标志未被改变、`healthy` 未进入最终 completed 判断，也是通用完备性局限；本次六条 healthy 均为真，因此未据此否定已报告结果。报告是在每 seed 冻结后评分、每时钟集成，而非等全部六组冻结才读取 review；未见代码将这些分数反馈到后续拟合配置，不能因此声称已经发生了结果导向调参。
