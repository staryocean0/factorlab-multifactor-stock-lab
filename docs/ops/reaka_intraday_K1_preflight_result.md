## 容量与有效样本

四相位H20重叠调整后，时间下界 `n_eff=69`；时间×截面平方根的设计值
约2,533.34，截面上界约88,000.25。三个预注册容量根均保留：

- `d8-h8`：最保守 `n_k_eff/d²=1.078`，预训练支持充足；
- `d16-h16` 与 `d16-h32`：最保守比值均为0.270，只能作
  `thin_claim_limited`候选；
- P6.4必须补签真实 `n_k_eff/d²`、Koopman矩阵条件数和成员/输入扰动
  稳定性，本步不声称d16算子可识别。

## LR、梯度和后端

两个时钟得到相同的首个不健康点前最大健康LR：`d8-h8=0.1`、
`d16-h16=0.03`、`d16-h32=0.03`；无右截断，未剪裁梯度有限。

ROCm与CPU的score最大绝对差为 `2.09e-7 / 1.81e-7`，Spearman均约
`0.9999999998`，数值门通过。两后端预热后交替运行5个计时块，每块4次负载；
中位数口径下14:30 CPU/ROCm为 `1.374/0.259s`（ROCm约5.31x），14:45为
`2.204/0.218s`（约10.13x）。两时钟都超过1.10x切换门，因此当前选ROCm。

## 基础设施事件

1. 首次冻结误假定P6.2存在时钟顶层manifest，在合同生成前fail closed；
2. 首轮后端预检用了系统CPU Python，未触发项目ROCm环境；
3. 改用ROCm 7.2后发现MIOpen不允许eval-mode RNN backward，修正为统一train mode后
   重冻合同并重放；
4. 主控关闭前发现兼容证书缺 `q_x/q_s`、`n_eff/d²`与后签义务，
   扩充证书和validator后再次从合同完整重放。
5. 验收后的targeted basedpyright发现8个JSON显式类型收窄错误，原关闭回执被撤销，
   补齐类型后所有目标文件为0 errors / 0 warnings；
6. 单计时块会使CPU/ROCm入选在重放间翻转，改为5个交替块的中位数并加
   1.10x切换门后重冻、重放。

所有事件都发生在正式训练前，无模型分数、账户或科学结果权。
